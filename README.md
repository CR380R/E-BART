# E-BART

E-BART is a model that predicts whether a statement is true or false and generates an explanation for its prediction. It builds on BART and was introduced in [*E-BART: Jointly Predicting and Explaining Truthfulness* (TTO 2021)](https://air.uniud.it/handle/11390/1213041). The later journal paper, [*A Neural Model to Jointly Predict and Explain Truthfulness of Statements* (JDIQ 2023)](https://doi.org/10.1145/3546917), includes a larger evaluation with human participants.

This repository provides the model code, the data from the human evaluation, and the task configurations. It follows the structure of the [published Chapter 10 dataset on OSF](https://osf.io/jr6vc/). The seven files from the original E-BART repository are preserved unchanged in [`Historical/`](Historical/).

## Model and Training

The best place to start is [`Source Code/E_BART_Final.ipynb`](Source%20Code/E_BART_Final.ipynb). It shows the model, data preparation, training and inference. The Python scripts in `Source Code/` provide the same main components.

E-BART uses Hugging Face BART to produce a truthfulness prediction and a written explanation. Training can use the standard `Seq2SeqTrainer`. For inference, the original implementation provides a `CustomTrainer` to handle the two outputs.

The model was originally trained using the [e-FEVER dataset described by Stammbach and Ash (2020)](https://dblp.org/rec/conf/tto/StammbachA20). The full training dataset and trained model weights are **not included**. The repository also does not provide a tested environment for current PyTorch and Transformers versions.

The training scripts expect records with the fields `id`, `label`, `claim`, `retrieved_evidence` and `summary`. The label is an integer, the evidence is a text passage, and the summary is the reference explanation. The input to BART takes this form:

```text
<s> claim </s> evidence </s>
```

The explanation is generated in the form `<s> explanation </s>`. The classification label is handled separately. See the notebook for preprocessing and training details.

## Human Evaluation

The journal study compares four ways of presenting a statement to participants:

| Condition | Information shown | Participant response |
| --- | --- | --- |
| V1 | Statement only | Truthfulness judgment and written justification |
| V2 | Statement and E-BART explanation | Truthfulness judgment and written justification |
| V3 | Statement and e-FEVER reference explanation | Truthfulness judgment and written justification |
| V4 | Statement and both explanations | Truthfulness judgment, written justification and explanation preference |

In V4, the **reference explanation appears first** and the **E-BART explanation second**. A preference of `1` (`first`) selects the reference explanation, while `2` (`second`) selects E-BART.

Each condition contains **52 statements**, with 26 labeled `SUPPORTS` and 26 labeled `REFUTES`. There are **130 task units** per condition, with four statements in each unit. The data contain **520 judgments per condition**, or **2,080 judgments from 514 distinct workers** in total.

V1, V2 and V3 use the same 52 statements. V4 uses 34 of those statements and 18 different ones. Across all conditions there are **70 distinct statements**. Every statement in V4 has two different explanations.

The study labels `SUPPORTS` and `REFUTES` describe the reference answer. They are different from the participant's `True` or `False` response.

## Crowdsourcing Task

The `Crowdsourcing Task/` folder contains four folders, `V1/` through `V4/`. Each includes:

- `instructions_main.json`: instructions shown to participants.
- `dimensions.json`: questions, answer values and justification settings.
- `task.json`: task settings and which information was visible.
- `hits.json`: the 130 units and the order of their four statements.
- `search_engine.json`: search interface settings, not saved searches.

The shared files `instructions_dimensions.json` and `questionnaires.json` are empty lists because those components were not used.

Each document in `hits.json` contains its statement, reference label and both explanations, even when a condition did not show every field. In `task.json`, `gt_explanation` identifies the reference explanation and `explanation` identifies the E-BART explanation. These correspond to `reference_explanation` and `ebart_explanation` in `Explanations.csv`.

All four conditions ask participants to choose `False` (`0`) or `True` (`1`) and provide a written justification of at least five words. V4 also asks which explanation they prefer. The reference label is not shown as the participant's answer.

## Worker Data

The five CSV files in `DataFrame/` contain records from all four conditions. Use the `task` column to identify V1, V2, V3 or V4. Worker identifiers are consistent pseudonyms across the tables.

| File | V1 | V2 | V3 | V4 | Total |
| --- | ---: | ---: | ---: | ---: | ---: |
| `workers_answers.csv` | 520 | 520 | 520 | 520 | **2,080** |
| `workers_acl.csv` | 130 | 130 | 130 | 130 | **520** |
| `workers_comments.csv` | – | – | 87 | 103 | **190** |
| `workers_mturk_data.csv` | 130 | – | 129 | – | **259** |
| `workers_user_agents.csv` | 130 | 130 | 129 | – | **389** |

A dash means that no corresponding records are included in the release.

`workers_answers.csv` contains one row for each judgment. It records the participant's answer, written justification, statement ID, position in the task, access count and assessment time. **2,079 of the 2,080 judgments have a written justification.** In V4, the same table also records explanation preferences.

`workers_acl.csv` contains one record for each selected task completion. Each completion is linked to four judgments. It includes available attempt, validation and submission information. `workers_comments.csv` contains comments about a completed task, rather than justifications for individual statements.

`workers_mturk_data.csv` contains available assignment and task metadata. `workers_user_agents.csv` contains browser, operating system and device categories. The source records do not cover every condition. In V3, MTurk metadata cover 128 of 130 completions; one completion has two possible assignment records. These records must not be treated as a unique match to a particular judgment.

To connect judgments with their completions and comments, use the combination of `task`, `worker_id`, `batch_name` and `unit_id`. Each completion has four judgments. Match `doc_id` to the statement tables. Do not join the MTurk or browser tables directly to judgments without checking for multiple matches.

## Statements and Explanations

`Ground_Truth.csv` lists the 70 statements, their study reference labels and possible identifiers from the official FEVER dataset. The `doc_id` values are local study identifiers, not official FEVER IDs. Exact text matching gives 63 statements with one candidate FEVER ID and seven with multiple candidates. For `claim_43`, different matching FEVER records have conflicting labels. The file preserves these possibilities rather than choosing an uncertain ID.

`Explanations.csv` contains the e-FEVER reference explanation and E-BART explanation for each statement. **17 pairs contain identical explanations**. None of those pairs appears in V4.

These files document the human evaluation. They are not a replacement for the full e-FEVER training dataset.

## Using the Data

Read identifiers as text. This example combines the judgments, statements, explanations and completion information without changing the number of judgments:

```python
import pandas as pd

options = {"dtype": str, "keep_default_na": False}
answers = pd.read_csv("DataFrame/workers_answers.csv", **options)
claims = pd.read_csv("Ground_Truth.csv", **options)
explanations = pd.read_csv("Explanations.csv", **options)
completions = pd.read_csv("DataFrame/workers_acl.csv", **options)

data = answers.merge(claims, on="doc_id", validate="many_to_one")
data = data.merge(explanations, on="doc_id", validate="many_to_one")
data = data.merge(
    completions,
    on=["task", "worker_id", "batch_name", "unit_id"],
    validate="many_to_one",
)
assert len(data) == 2080
```

Filter the `task` column to study a single condition.

## File Integrity and Reuse

`release_manifest.json` lists 39 study files and their checksums. `checksums.csv` lists **40 SHA256 hashes**, including the manifest. The checksum file itself is excluded.

The scientific data, task files and model code have the same contents as the [published OSF release](https://osf.io/jr6vc/). The README is adapted for this GitHub repository, so the manifest and checksums also reflect the updated documentation. The original public repository files are preserved separately in `Historical/`.

Worker IDs are pseudonyms, not guarantees of anonymity. Written responses, timestamps and technical metadata can still carry privacy risks. Do not attempt to identify or contact participants. The files also contain material with different reuse conditions. Read [`RIGHTS.md`](RIGHTS.md) before redistribution.
